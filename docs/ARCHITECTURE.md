# 구조와 설계 결정

이 문서는 구현 기준을 정한 설계 문서다. 앱, APK, 서버 또는 실제 문자 발송이 완성됐다는 뜻은 아니다. 화면 구성은 [UI_UX.md](UI_UX.md), 구현 순서와 완료 조건은 [ROADMAP.md](ROADMAP.md)를 따른다.

## 1. 제품과 기술 기준선

주 사용 환경은 회장의 안드로이드 앱이다. 홈·회원·행사·회비·연락의 다섯 탭과 우측 상단 설정을 사용한다. 인터넷이 없어도 회원 관리, 행사 작성, 회비 기록, 템플릿 작성과 이력 확인이 가능해야 한다. 회원용 웹은 앱 설치 없이 참석 응답·일정 투표·안내 확인·입금 확인 요청을 제출하는 작은 서비스로 구축한다.

| 영역 | 기준선 | 책임 |
| --- | --- | --- |
| 안드로이드 | Kotlin, Jetpack Compose, Room | 운영 화면, 로컬 데이터, 메시지 작성, 공유 실행 |
| 회원용 웹 | React, TypeScript, Vite | 휴대폰에서 링크를 열어 응답하는 화면 |
| 단일 서버 | Node.js, TypeScript, Fastify, SQLite | 웹 제공, 운영자 인증, 행사 공개본, 응답 저장·동기화 |
| 기본 작성 기능 | 템플릿, 변수 치환, 조건 필터 | 외부 LLM API 없이 공지 작성 |

웹 빌드 결과와 API는 같은 서버에서 제공한다. 초기 규모에 별도 메시지 브로커, 마이크로서비스, 관리형 유료 서비스를 요구하지 않는다. 호환되는 안정 버전과 의존성 잠금 파일은 구현 시 확정한다. 기존 프로젝트의 재사용은 접근·변경 권한과 구조의 적합성이 확인된 경우에만 진행한다.

저장소는 `apps/android`, `apps/web`, `apps/server`, `docs`로 구분한다. 안드로이드 내부에서는 화면, 업무 규칙, 데이터 저장, 외부 공유 실행을 나누되, 파일과 모듈을 필요 이상으로 분리하지 않는다.

## 2. 문자와 카카오톡 실행 경계

문자의 기본 실행은 `ACTION_SENDTO`와 `smsto:`를 이용해 문자 앱에 수신자와 본문을 넘기는 방식이다. 사용자는 최종 수신자·내용·SKT 회선을 확인하고 문자 앱에서 직접 전송한다. 기본 구성에 `SEND_SMS` 권한이나 무인 발송 기능을 넣지 않는다. 입력한 발신번호가 실제 회선을 바꾸는 것처럼 표현하지 않는다.

개인별 문구는 수신자별 작업으로 관리한다. 여러 번호를 한 대화에 넣어 그룹 문자로 보내지 않고, 다음 수신자를 사용자가 확인하며 진행하게 한다. 문자 앱마다 본문 전달, 장문 처리, 회선 선택 동작이 다를 수 있으므로 실제 단말 확인이 필요하다. SKT 요금제와 이용 조건은 별도 확인 사항이며, 무료·무제한 발송을 보장하지 않는다.

카카오톡은 공식 SDK의 지원 범위 안에서 사용자가 대화 상대나 방을 선택하는 공유 흐름을 제공한다. SDK 설정이 없거나 실행할 수 없으면 일반 안드로이드 공유로 전환한다. 전화번호 목록으로 임의의 상대에게 자동 전송하거나 대화방을 자동 조작하는 기능은 설계에 포함하지 않는다.

`초안`, `문자 앱 열림`, `공유 화면 열림`, `사용자가 발송했다고 표시`, `실행 실패`, `결과 미확인`을 구별한다. 외부 앱에서 돌아왔다는 이유로 실제 전송·전달·읽음을 확정하지 않는다. 회원이 웹에서 제출한 `안내 확인`도 메시지 전달 상태와 별개다. 발송 이력은 당시 대상과 문구의 스냅샷을 보관한다. 중복 누름은 막되, 결과가 불명확한 작업을 자동 재전송하지 않는다.

## 3. 데이터 소유권과 동기화

| 데이터 | 원본 관리 위치 | 변경 원칙 |
| --- | --- | --- |
| 회원, 그룹, 회비 원장, 템플릿, 연락 이력 | 운영자 앱의 Room | 첫 버전은 한 운영자 기기에서 관리 |
| 행사 기획과 참가 대상 | 운영자 앱 | 서버에는 필요한 공개 정보만 게시 |
| 게시된 행사의 참석 응답, 일정 투표, 안내 확인 | 서버 | 제출 이력과 버전을 보존하고 앱으로 동기화 |
| 입금 확인 요청과 검토 상태 | 서버 | 회원의 주장을 접수·전달하며 검증된 납부 원장과 분리 |
| 게시 전 수동 참석 응답 | 운영자 앱 → 최초 게시 후 서버 | 최초 업로드가 확인된 뒤 서버 버전을 사용 |

모든 엔터티는 전화번호와 무관한 고유 ID를 갖는다. 번호 표기는 정규화하되 중복 번호를 이유로 회원을 조용히 합치지 않는다. 회비는 부과·납부 확인·면제·정정 기록으로 관리하고, 정정 이유와 시점을 남긴다. 회원의 입금 알림만으로 납부 완료를 만들지 않는다.

앱은 웹 반영이 필요한 변경을 로컬 대기함에 저장한다. 변경마다 작업 ID, 대상 ID, 기준 버전을 두고 서버가 중복 작업을 재적용하지 않게 한다. 응답 동기화에는 이어받기 위치를 저장한다. 네트워크가 끊겨도 로컬 작업을 보존하고 `동기화 대기`와 최근 동기화 시각을 표시한다.

게시 전 수동 참석 응답은 최초 게시 시 고유 작업 ID와 운영자 작성 표시를 함께 업로드한다. 서버가 수락한 응답 ID·버전을 돌려준 뒤 서버를 원본으로 전환한다. 이미 게시된 행사의 응답을 운영자가 오프라인에서 수정하면 작성 주체와 기준 버전이 있는 제안 변경으로 보관한다. 그 사이 회원이 웹 응답을 바꾸면 양쪽 기록을 검토해 확정하며, 운영자 변경을 무조건 우선하거나 시각만으로 덮어쓰지 않는다. 미확정 변경은 앱에서 동기화 대기로 표시한다.

입금 확인 요청은 회원이 주장한 금액·입금자명·시각과 검토 상태를 기록한다. 운영자가 실제 입금을 확인하면 앱의 회비 원장에 별도 고유 납부 기록을 만들고 요청 ID와 연결한 뒤, 서버에 검토 결과를 전달한다. 동기화 재시도로 납부가 중복 계산되지 않게 하며, 반려·정정은 기존 이력을 보존한다.

버전이 다른 수정은 충돌로 드러낸다. 회비나 행사 내용을 단순히 마지막 저장 시각으로 덮어쓰지 않는다. 첫 버전의 회비 원장은 서버에서 수정하지 않으며, 향후 여러 운영자를 지원할 때도 충돌 항목은 원장 이력과 함께 검토하게 한다. 행사 일시 등 중요한 정보가 변경되면 기존 응답을 삭제하지 않고 이전 행사 버전에 대한 응답임을 표시해 재확인을 요청할 수 있게 한다.

## 4. 회원용 웹과 운영

웹은 참석 응답·일정 투표·안내 확인·입금 확인 요청에 집중한다. 앱의 전체 관리자 기능을 복제하지 않는다. 초대 링크에는 예측하기 어려운 토큰을 사용하고, 서버에는 토큰 원문 대신 검증용 값을 저장한다. 토큰의 행사·대상·허용 동작·만료 범위를 검사한다. 링크와 화면에 전화번호나 다른 회원 명단을 노출하지 않는다.

공통 행사 링크는 가입·로그인 없이 미확인 신청을 받는다. 운영자는 행사 참여자의 확인 대기에서 실제 회원과 확인해 연결하며, 이름·전화번호 입력만으로 기존 응답을 덮어쓰지 않는다. 공통 링크의 제출에는 자기 제출만 수정할 수 있는 제한 토큰을 발급한다. 개인 초대 링크의 제출은 정해진 회원 범위로 접수하며, 입금 확인 요청과 개인 회비 안내는 이 경로에서만 제공한다. GET·링크 미리보기·스크랩 요청은 어떤 응답 상태도 바꾸지 않는다.

일정 투표는 후보 날짜에 대한 복수 선택과 마감 전 수정으로 작게 시작한다. 투표 종료만으로 행사 일시를 바꾸지 않고, 운영자가 별도 확정하며 기존 참석 응답과 관련된 변경 내역을 남긴다.

행사 마감, 행사 취소, 토큰 만료, 제출 완료는 서로 다른 상태다. 마감 후에는 변경을 막고 기존 응답을 보여 주며, 취소·만료 시에도 이유를 알 수 있게 한다. 동시에 열린 화면의 수정은 버전을 확인하고 최신 응답을 보여 준 뒤 재확인하게 한다. 취소하거나 대상에서 제외한 초대의 제출 권한도 갱신한다.

서버는 HTTPS, 운영자 인증, 비공개 데이터 저장과 백업 경로를 갖춰야 한다. 회원이 응답할 때 회장의 앱이 켜져 있을 필요는 없다. 서버를 연결하지 않았거나 장애가 발생해도 앱의 로컬 기능은 유지한다. 기존 서버 활용에는 권한 확인이 필요하며, 공개 GitHub 저장소 생성 권한을 공개 서비스 배포 권한으로 해석하지 않는다.

## 5. 공개 소스와 선택 기능

저장소에는 코드, 설치 안내, 설정 예시, 가상 데이터와 검증 기록을 둔다. 실제 회원 데이터, 전화번호, 문자 기록, 데이터베이스, 로그 속 개인 정보, 비밀키와 앱 서명키는 포함하지 않는다. 데이터 내보내기와 복원은 사용자가 선택한 비공개 파일로 처리하고 GitHub를 데이터 백업으로 사용하지 않는다.

기본 기능은 외부 LLM API에 의존하지 않는다. 로컬 모델은 추후 선택 기능이며 특정 PC나 GPU의 상시 가동을 전제하지 않는다. 알림은 운영자가 확인할 업무를 알려 주는 수단으로 설계하고 무인 문자 발송으로 연결하지 않는다.


## 6. 첫 구현의 실제 경계 (2026-10-12)

Android AppDatabase/Room은 회원·행사·원장·템플릿·초안·공유 스냅샷을 소유한다. RemoteApi는 수동 행사 게시/초대/응답 스냅샷만 제공한다. 작업 ID와 본문을 저장해 게시 재시도를 지원하지만 자동 동기화 대기함/커서/충돌 검토 전체는 아직 없다. 수동 RSVP가 있는 최초 게시와 게시 후 로컬 RSVP 수정은 이관 기능 전까지 차단한다.

서버 Store는 SQLite 트랜잭션과 암호화 재시도 영수증을 사용한다. 관리자 인증은 라우트에 직접 부착하고 회원 링크는 행사/회원/동작/만료로 제한한다. GET은 상태를 변경하지 않는다. 일반 링크 신청은 명시적 검토 없이 회원과 연결하지 않으며 입금 요청은 원장과 별개다. 웹은 링크별 미확인 요청을 세션에 보관하고 이전 행사 버전 응답을 표시한다.

상위 절은 목표 설계이며 모두 구현됐다는 뜻이 아니다. 실제 지원/남은 작업/CI/실기 구분은 STATUS.md와 API.md를 기준으로 한다.
